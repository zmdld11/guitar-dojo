# 节拍器漂移测量

> 对应 issue #8。目标：证明「长时间播放不漂移」不是靠耳朵，而是有可复现的数据。

## 1. 已经被单测覆盖的部分

调度本身是**帧级精确**的，不依赖系统时钟：

| 测试 | 验证内容 |
| --- | --- |
| `BeatTimelineTest.400 拍之后仍无累积误差` | 400 拍逐拍比对理论帧号，误差 < 1 帧 |
| `BeatTimelineTest.拍点帧号严格递增` | 300 BPM 四细分下连续 200 个拍点严格递增 |
| `MetronomeMixerTest.拍点落在缓冲区的实际偏移上` | 拍点落在缓冲区内的确切偏移，静音块全零 |
| `MetronomeMixerTest.运行中改速度下一个拍点保持原时刻` | 拖 BPM 不会连续重触发 |

这些保证「写进 AudioTrack 的波形」是按采样点排布的。

## 2. 需要真机验证的部分

AudioTrack 之后是设备音频通路：缓冲区欠载、系统调度、蓝牙延迟都会影响实际出声。
这部分必须在**真机**上测，模拟器的音频时钟不可信。

### 步骤

1. 安装 debug 构建（release 不安装该日志钩子）：

   ```bash
   ./gradlew installDebug
   ```

2. 清空日志并开始采集：

   ```bash
   adb logcat -c
   adb logcat -s MetronomeDrift > drift.txt
   ```

3. 打开 App → 工具 → 节拍器 → 开始，**保持播放 30 分钟**（可锁屏，验证后台播放）。
4. 停止播放，`Ctrl+C` 结束采集。
5. 分析：

   ```bash
   python tools/analyze_drift.py drift.txt --sample-rate 48000
   ```

6. 把输出贴进 issue #8，并记录设备型号、系统版本、是否蓝牙输出。

### 判定标准

| 指标 | 合格线 | 说明 |
| --- | --- | --- |
| 间隔标准差 | < 2 ms | 直接影响听感；这是核心指标 |
| 累计漂移峰值 | < 20 ms | 相邻拍点相对理论时刻的瞬时偏差上限 |
| 漂移斜率 | 绝对值 < 100 ppm | 系统时钟与音频时钟不同源会带来恒定斜率，属硬件特性；显著非零时看标准差是否仍合格 |
| AudioTrack 欠载 | 0 | 非零说明缓冲太小或线程被抢占 |

### 如果超标的排查顺序

1. 欠载非零 → 加大 `MetronomeEngine` 的 `bufferBytes` 倍数（当前为 `minBufferSize * 2`）。
2. 间隔标准差大但欠载为 0 → 检查轮询线程是否被限流；当前轮询间隔 4 ms，可降到 2 ms。
3. 只在锁屏后变差 → 检查前台服务是否被系统降级（Doze / 厂商省电策略）。

## 3. 日志格式

```
10-24 09:30:00.123  1234  1250 D MetronomeDrift: 123456,9876543210000
                                                 帧号     elapsedRealtimeNanos
```

帧号来自给 AudioTrack 的写入计数（音频时钟），纳秒来自系统时钟，因此二者的差值变化就是漂移。

## 4. 已知局限

- 测量的是「音频回调时钟 vs 系统时钟」，不是「扬声器实际出声时刻」；后者需要外部录音设备比对。
- 蓝牙耳机有 100-300 ms 固定延迟，属正常现象，不影响节奏稳定性判断，但会让「拍点视觉同步」看起来偏早。
