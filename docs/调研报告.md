# 立项调研报告

> 调研时间：2026-10-24。目的：为 guitar-dojo 的技术选型、数据源方案与训练内容设计提供依据。
> 结论已落到 `docs/ROADMAP.md` 的决策与 issue 中；本文件保留调研过程与可复查的出处。

## 一、本地资产调研：MUSE 项目可复用性

### 1. 项目概况

`D:\program_project\MUSE`（聆谱 MUSE v0.1.0-pre）是本人此前大创做的 AMT 自动扒谱系统，技术栈：

- 后端 Python（torch / demucs / librosa / pretty_midi），虚拟环境在 `MUSE/env`；
- 前端 React 18 + Vite + TypeScript + Tailwind + zustand + OSMD（五线谱渲染）+ smplr/@tonejs/midi（MIDI 合成）+ Tauri 2；
- 管线：音频 → 乐器分离（VER-SEP / Demucs）→ 多乐器转写 → 量化记谱（MusicXML）→ 三视图播放器。

**结论：不做整体复用**。MUSE 是桌面端 Python 管线 + Web 前端，与安卓原生 App 技术栈不通；但其**算法模块与谱子数据**可离线借鉴或作为转换输入。

### 2. 可复用模块清单

位于 `MUSE/score_extraction/src/`：

| 模块 | 用途 | 对本项目的价值 |
| --- | --- | --- |
| `gpif_parser.py` | Guitar Pro 7/8 `.gp` 解析器（→ JSON / 参考 MIDI，含 tempo map、时值、内嵌音频提取） | **最高**：M3 转换器的参考实现 |
| `guitar_tab.py` | 吉他 TAB 排指算法 `assign_guitar_fingering`（MIDI 音高 → 弦品位置） | **高**：为无指法标注的谱补排指 |
| `beat_track.py` / `bpm_detect.py` | 节拍跟踪 / BPM 检测 | 中：离线校验乐句 BPM |
| `quantize_timing.py` | onset 对齐节拍格点的时值量化 | 中：M5 考核的判定思路可对照 |
| `transcriber.py` / `frame_post.py` / `note_post.py` | 自训 OnsetsAndFrames 转写与后处理 | 低：模型体积与算力不适合端上，暂不用 |
| `chord_detect.py` / `key_estimate.py` | 和弦识别 / 调性估计 | 低：1.0 后和弦考核可参考 |
| `beat_track` 等 librosa 依赖 | — | 仅离线工具可用 |

**注意**：MUSE 内没有传统单音音高检测（pYIN/YIN）模块——音高全部走神经网络转写。因此 M2 的音高检测需**自行实现或引入 TarsosDSP 类库**，不能从 MUSE 直接搬。

### 3. 谱子资产清单（MUSE/music）

共 23 个谱子类文件，另有 29 个 flac 音频。

| 目录 | 文件 | 格式与可用性 |
| --- | --- | --- |
| `Songsterr/` | 6 个 `.gp` | **Guitar Pro 8**（zip 内 `Content/score.gpif` XML，alphaTab 写出，来源 Songsterr 抓取）。曲目：星座になれたら(123 BPM)、quantum jump(130)、虚無の先で愛を見つける(81)、地球最後の告白を(160)、夢と色でできている(167)、红莲华(135)。**版权风险：不可入库** |
| `guitar/` | 1 `.gp` + 1 `.tg` + 1 `.mscz` + 4 `.png` | `.gp` 内嵌 20MB FLAC；`.tg`（TuxGuitar）是 MUSE 管线机器生成（"GuitarOMR Output"）；`.mscz` 为 MuseScore 转换件；png 为 4 页指弹谱图 |
| `piano/` | 3 `.mid` + 1 `.txt` | 标准 MIDI（卡农变奏，70–80 BPM，钢琴轨）；`.txt` 为自定义简谱文本格式，需专门解析器 |
| `vocal/` | 6 `.lrc` | 歌词，对吉他练习价值低 |

**Guitar Pro 谱的字段完整度（抽查「红莲华」）**：Title / Artist / Tempo automation(135) / 810 小节 / 6 轨（GT1 木吉他、GT2 失真吉他、贝斯、鼓、GT3 失真等）/ 每轨定弦 Pitches(38 45 50 55 59 64) / CapoFret / FretCount 24；**每个音符带 String + Fret**，含 Slide 等技巧标注 71 处；**缺左右手指法标注**（需排指算法补）。

### 4. 结论

1. **最佳数据源**：7 个 Guitar Pro 文件——元数据、小节、音符弦品俱全，且都是本人喜欢的流行曲（红莲华、星座になれたら），符合「弹爱听的歌更开心」的动机设计。
2. **版权处理**：这些是 Songsterr 抓取件，**只作个人本地练习用**，转换后的 JSON 同样不入公开仓库。落地方式见 ROADMAP #16 / #20 与 `.gitignore` 的 `local_phrases/`。
3. **转换在电脑上做**：App 不内嵌 Python，`tools/` 下离线脚本把 `.gp` 转成 JSON Schema，App 只读取 JSON。

## 二、线上同类项目调研

### 1. 开源吉他练习 App

| 项目 | 技术栈 | 功能范围 | 可借鉴点 |
| --- | --- | --- | --- |
| [Lfrangt/fretflow-ui](https://github.com/Lfrangt/fretflow-ui) | Web（前端） | 双语指板、可编辑和弦进行、音视频分析扒谱、谱面导入导出 | 指板交互与谱面导入的产品形态；**名字撞车，故本项目弃用 FretFlow** |
| [prakhar1989/fretflow](https://githublb.vercel.app/repo/prakhar1989/fretflow) | Web | 指板可视化、调弦学习 | 仅作参考 |
| [PitchKit](https://github.com/NicosNicolaou16/PitchKit) | Kotlin（Android） | 实时吉他调音 + 和弦检测（麦克风输入） | **M2 的直接参考**：Kotlin 优先、专为吉他调参 |
| [MIDI-Voyager](https://github.com/DevanWolf/MIDI-Voyager) | Android | SoundFont MIDI 播放器，带 FX、和弦分析、MIDI IN/OUT | **M3 的参考**：安卓端 SoundFont 合成方案 |
| [SpessaSynth](https://github.com/spessasus/SpessaSynth) | TS/JS | SF2/DLS 实时合成器 | 合成器参数与实现思路参考（非安卓原生） |

**共性发现**：开源生态里「调音器」「MIDI 播放器」「指板可视化」都是成熟单品，但**几乎没有把「每日训练计划 + 进度自适应 + 考核」串成闭环的开源项目**。这正是本项目的差异点，也是主要工作量所在。

### 2. 安卓音高检测方案

- **TarsosDSP**（Java）：经典方案，内含 YIN 与 McLeod Pitch Method（MPM），通过 `PitchProcessor` 可在 Android 使用。教程与案例多（[Medium 教程](https://medium.com/@juniorbump/pitch-detection-in-android-using-tarsosdsp-a2dd4a3f04e9)）。
- **PitchKit**（Kotlin）：较新的 Kotlin-first 库，直接面向吉他调音与和弦检测。
- **自实现 YIN/MPM**：算法本身不复杂，参考实现多，便于针对吉他做定制调参并写单元测试。

**吉他泛音误判问题**（本人抱怨现用 Play 调音器对泛音敏感）的行业通行对策：

1. **倍频/八度误差抑制**：多周期联合估计，避免把 2f/3f 判为基频；
2. **置信度门限**：MPM 的 clarity / YIN 的 aperiodicity 低于阈值时不出结果（宁可不显示，也不错报）；
3. **中值/滑窗平滑**：去除单帧跳变；
4. **能量门限**：低于阈值视为噪声；
5. **低频优先**：电吉他 E2(82.4 Hz) 起，窗口至少覆盖 3–4 个基频周期（~40 ms 以上）。

**结论**：M2 自实现 YIN 或 MPM（倾向 MPM，抗噪与八度误差表现更适合吉他），上述 5 条策略作为 issue #12 的实现清单，并以合成信号单测 + 真机主观对比双重验收。

### 3. 吉他训练体系的通用结构

参考 JustinGuitar 模块化初级课程、社区练习计划讨论、《365日电吉他手的养成计划》：

- **单次训练结构**：热身（warm-up，3–5 分钟，手指与拨弦激活）→ 技术专项（technique，一个明确目标）→ 应用（song/riff 片段，把技术用出去）→ 收尾。
- **周期结构**：模块化进阶——每个模块有明确技能点，掌握后进入下一模块；每日练习项固定但内容轮换。
- **关键洞察**：初学者放弃的最常见原因是**难度断层**（本人正是被《365日》第二周劝退），因此本项目把「自适应降速/重练」做成一等公民，而不是可选项。

**落地**：M4 的训练向导按「热身 → 技术 → 乐句 → 考核 → 收尾」五段组织；M5 考核结果直接驱动难度调整；难度档位取「帅帅教程」与「365日」之间。

### 4. 变速播放与跟弹考核技术

- **变速播放**：MIDI 播放变速的可靠做法是**改时间轴而非改采样率**（避免音高变化）——重算每音符的起始 tick 与时长，再用 SoundFont 实时合成；循环通过重置播放指针实现。参考 [MIDI-Voyager](https://github.com/DevanWolf/MIDI-Voyager)。
- **节拍器精准调度**：Android 上 `Handler.postDelayed` / `Timer` 会漂移，正确做法是**基于音频回调时钟**（AAudio/Oboe 的帧计数与 timestamp）在音频线程内调度，配合预混样本。这是 M1 的核心技术点（issue #6）。
- **跟弹考核**：开源界主流思路是「音高序列 + 时间对齐」两段式：
  1. 逐帧取音高（M2 引擎）→ 分割为音符事件；
  2. 与目标谱做**单调对齐**（动态时间规整 DTW 或简单贪心匹配），得到音高匹配率；
  3. 节奏分用 onset 相对节拍格点的偏差（毫秒/百分比）计分。
  单声部单音乐句可行性高，和弦判定留待 1.0 后。

**结论**：M1 用音频时钟调度；M3 变速走「时间轴重算 + 实时合成」；M5 用「音高序列 + 格点偏差」评分，先从单音起步。

## 三、调研对决策的影响汇总

| 决策点 | 调研结论 |
| --- | --- |
| 技术栈 | Kotlin + Compose：音频回调、DSP、前台服务均为原生强项；Web/RN 方案在低延迟音频上要写原生模块，反而更重 |
| 数据源 | MUSE 的 7 个 GP 谱 + 自编基础乐句；转换离线做；版权谱本地存放不入库 |
| 音高检测 | 自实现 MPM/YIN + 5 条抗泛音策略；PitchKit/TarsosDSP 作参考 |
| 计划引擎 | 纯算法规则：开源界无成熟「自适应每日训练」方案可抄，规则引擎可完全掌控且可测 |
| 难度曲线 | 取「帅帅」与「365日」之间，自适应降速为核心机制 |
| 内容形态 | 手型图用黑白简笔画（Bits & Bops 风格），关键帧分格 + 要点标注 |
